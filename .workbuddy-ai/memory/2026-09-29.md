### ⚠️ 踩坑：BOM 污染，以及"纯度检查本身的盲区"

- 用 Python **默认方式读**（universal newlines）再以 `newline=""` 写，会给**原本没有 BOM** 的文件加上 BOM。
  本次 76 个文件每个都多出一行 `-using … / +﻿using …`，diff 立刻被污染
  （虽然每文件增删仍对称，很容易漏看）。
- 更麻烦的是：**第一版纯度检查用 `utf-8-sig` 解码**，恰好把 BOM 差异一并抹掉，
  于是 75 个文件"看起来"逐字相同——**检查方法自身有盲区，等于没检查**。
- **正确做法**：改名/搬家这类操作，全程按**字节**处理与比对（替换串都是 ASCII，不需要解码）。
- 换行符这次**没变**（`git ls-files --eol` 显示 `i/lf w/lf` 一致）；那些
  `LF will be replaced by CRLF` 是仓库 `core.autocrlf` 的固有提示，不是本次造成的。
- 另一类脚本坑复现：**只算计数、写回的却是原串**（`subn` 结果没用上），
  靠"改完 grep 残留"才发现——**任何批量改写都必须用残留 grep 收尾**。

  改成租约要在边界处整帧复制一次（整图 ≫ ROI 裁图），**复制量反而变大**。
  这印证了用户"继续复印"的裁决是对的。
- **但训练路径现在确实重复复制 3~4 次**（`RegionAnomalyDetector.cs:69`）：
  `g.Crop(rect)` 分配+拷贝 → `new PixelSnapshot` 构造**再 Clone 一次** → `CopyPixels()` 又一次
  → `VisionImage.CopyFrom`（是否再拷待确认）。真收益在这里：**让快照只被"读"，不再被"裁剪成第二张图像"**。
- `AnomalyLibraryControl.cs:512-516` 的 `Translate(g, s.X, s.Y)` 返回**新 `PixelSnapshot`**，
  谁持有/谁负责其生命周期需要先定。

### 方案评审实测前提（"Vision 常驻缓存 + 持久化时才编码"）

- **`ToLabel` 是 2 份复制，不是 1 份**：`AlgorithmContractAdapter.cs:44-51` 先 `new byte[]` + `CopyTo`，
  再被 `PixelSnapshot` 构造器 `Clone` 一次 → `RoiSession.Quality.cs:248-270` 的"每字符 4 次 ToLabel"
  实际是 **8 份/字符**。
- **`ToVision` 是整帧复制**：`AlgorithmContractAdapter.cs:14-24` = `VisionImage.CopyFrom(..., frame.CopyPixels())`。
  热路径浪费量 = **ROI 数 × 字库字数** 份整帧（`RoiSession.Quality.cs:195-203`，每检测每 ROI 重建整个字库的租约）。
  → 方案第 2 步"缓存持租约、每 ROI 只 Retain"打的就是这里，方向正确。
- **字库没有"每 ROI 读盘解码"**：`InspectionStore.Snapshot`（`:858-915`）在**加载时**读 `png_base64`
  → 校验 `Hash(png) == sha256` → `_codec.Decode` → `PixelSnapshot` → `GlyphReference.Image`，之后常驻。
- **`GlyphReference.Sha256` = 存储 PNG 字节的哈希**（写入 `:212` / `:324` 用 `Hash(EncodePng(image))`）
  → "历史 PNG 哈希不变"可用现有字段断言，无需新字段。
- **"持久化时才编码"已是现状**：`report.json` 走 `JsonConvert.SerializeObject(report, _json)`，
  `_json` 上挂了 `Storage/Persistence/Internal/InspectionStore/FrameConverter.cs:33` ——
  序列化到哪张证据图就编码哪张（`png_base64`）。且 `SaveReport` **无产品调用者** →
  方案第 3 步省不到产品时间，唯一价值是为"改存编码字节"铺路。
- **报告证据像素的真实消费者是界面**：WinForms `Workbench/LabelInspectionControl.cs:1057-1062`、
  WPF `Workbench/LabelInspectionControl.cs:523-528` 读 `glyph.Character.Patch` 与
  `Comparison.Actual|Reference|Delta` 并直接画出来 → 报告模型必须持有"自己拥有像素、可长期不释放"的值，
  即 `PixelSnapshot` 的现有定义。**方案里"最终删掉 PixelSnapshot"与 `28fbb4f` 的决定冲突**，
  只有把证据载体换成编码 PNG 字节（`FrameConverter` 映射 `byte[]`、界面按需解码）才成立——
  这是唯一岔路口，必须在动手前先定。
- `DP.Vision` 编码器**仍不存在**（只有 `IImageFileReader` / `OpenCvImageFileReader`，解码返回租约）；
  第 1 步"补编解码"里解码是归位、编码是从零写，且其第一个真实调用者取决于上述岔路。
- 样板断言要改：**"同一版本反复比较只解码一次"现在恒真（根本不解码），测不出东西**。
  应改成：加载时每字 `Retain` 恰好 1 次 / 比较 N 次净租约不随 N 增长 / 逐出后归零 / 全程 `ToLabel` 为 0。
  且样板要挂在质检热路径 `TextQuality` 上，不要挂在字库加载上。

### 已落地：字库参考图按固定版本只转换一次（第 2 步样板）

**为什么没复用 `PinnedRevisionCache<T>`**：它没有逐出回调（放租约进去会在逐出时泄漏），

**⚠️ 新踩到的坑：重叠 ROI 会被工作流判 `roi_overlap` 并整体跳过质量阶段。**

看起来像"缓存没生效"，实际是该 ROI 根本没跑到质检。**多 ROI 用例必须用互不重叠的 bounds。**

| 变异 | 期望红灯 |
